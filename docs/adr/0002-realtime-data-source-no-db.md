# ADR-0002: 数据源采用"完全实时"模式,不持久化版本元数据

**状态**: Superseded by ADR-0010
**原日期**: 2026-08-28
**决策者**: 产品负责人 + 后端
**取代说明**: 引入"搜索/下载记录 + 热门榜单"需求后,后端必须持有 SQLite 用于事件持久化与聚合。原"无 DB"决策被推翻,详见 ADR-0010。

## 背景

VSCodeMarket 后端需要拉取:

- 客户端/服务端版本清单与下载地址
- 扩展元数据与 vsix 下载地址

候选策略:

- (a) 完全实时:每次请求调官方 API
- (b) 定时全量同步到 DB
- (c) 混合:版本号 DB + 扩展 API + CDN 透传
- (d) 构建期静态 JSON

## 决策

**采用 (a) 完全实时模式。后端不持有任何持久化的版本元数据。**

## 理由

- **数据源可控**:VSCodeMarket 部署在公网,可直接访问 `update.code.visualstudio.com` 与 `marketplace.visualstudio.com`。
- **零运维负担**:无须 DB、无须 cron、无须缓存失效。
- **永远新鲜**:无需考虑版本元数据过期。
- **轻量**:每个 API 调用单次响应小(版本号清单 ~100KB,扩展元数据几 KB)。

## 后果

- 每次请求耗时 = 1~N 次外部 API 串行调用。需要前端 Loading 状态。
- 官方 API 抖动会直接传导到用户体验。可接受:这些 API 都是微软基础设施,可靠性高。
- 扩展 vsix 文件本体仍走 302 跳转,后端不代理流量、不下载不缓存。
- 不引入数据库(此 ADR 一旦采纳,后续 plan 不应加 DB;如确需,起 ADR-0010)。

## 性能与降级

- 内存内可选地缓存版本清单(TTL 几分钟),减小上游压力——这是**缓存,不是 DB**,允许保留。
- 严禁引入 MySQL/Postgres/SQLite。

## 替代方案

- **(b) 定时同步**:否决。本场景无内网访问需求,失去离线能力没收益。
- **(c) 混合**:否决。引入 DB 但只存版本号得不偿失。
- **(d) 静态 JSON**:否决。版本号每天都变,重建成本高。
